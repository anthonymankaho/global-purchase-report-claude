## Resolved decisions and remaining design gate

1. **GitHub account - resolved 2026-11-02:** `anthonymankaho`. Private repositories `GPR-Web` and `GPR-Data` were created and cloned to `C:\Users\User\GitHub-Clones\GPR-Web` and `C:\Users\User\GitHub-Clones\GPR-Data`.
2. **Quota implementation selected:** the approved requirement (updated 2026-11-04) is a strict 5,000,000 provider-token monthly cap per AI app; the original KV counter was a builder implementation call. Use one strongly consistent Durable Object quota record per app/month. Atomically reserve a conservative maximum token allowance before each provider call, then settle valid replies to provider `usage`; settle no-response and non-2xx failures at zero, and charge the reserved upper bound for unusable or missing-usage 2xx responses. Bound both request and output size so the reservation is valid, fail closed on quota-store errors, and include concurrent-call verification. KV remains appropriate for report-version data, not the hard quota counter. Cloudflare documents KV as eventually consistent and unsuitable for atomic read/write transactions; SQLite-backed Durable Object storage is strongly consistent and transactional. See [Cloudflare KV consistency](https://developers.cloudflare.com/kv/concepts/how-kv-works/) and [Durable Object SQLite storage](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/).
3. **Data publication approach selected:** the design calls a two-key KV publication an “atomic swap.” KV does not provide a multi-key transaction. Use immutable period-versioned data plus a current-version pointer, retaining the previous version for rollback; document the propagation window and ensure a stale pointer still resolves to valid data. Do not overwrite the live data key before its replacement is ready.
4. **Cohort URL handling - implementation selected:** store SHA-256 path-segment hashes mapped to non-personal bucket names in the Worker secret `COHORT_MAP`, outside source control. Add/update that secret only when cohort links are issued or revoked. Treat each emailed path segment as a credential: avoid logging it, set a restrictive `Referrer-Policy`, and test revocation across the HTML, assets, API, and data routes. Preserve the accepted forwarded-link risk.

## Implementation sequence

### 1. Preflight and repository setup

- Confirm the GitHub owner/account and inspect both target repository names for collisions before creation.
- Recheck the local project status and compare the canonical folder with its remote before any push. Preserve any uncommitted or parallel-session changes.
- Create private `GPR-Web` and `GPR-Data` repositories and clone them beneath `C:\Users\User\GitHub-Clones\` only after the account decision is settled.
- Keep the WEB repository limited to Worker code, static shell/build inputs, deployment configuration, and non-secret examples. Keep versioned monthly JSON and its validation metadata in DATA.
- Add ignore rules and a pre-push leak scan for credentials and generated local configuration. Never place the Qwen token or cohort link map in either repository.

### 2. Define and validate the report data contract

- Trace how `build\src\core.js` and `build\src\main.js` consume the embedded `{fields, rows}` seed, including derived option sets, summaries, and period labels.
- Define a versioned JSON contract with `period`, schema version, fields, rows, and any metadata the dashboard requires. Export from the finalized Excel master as the source of truth; cross-check row/month counts and financial totals to `build\data\report-seed.json` without modifying it.
- Add a deterministic export/validation step at the existing Node build boundary or the authoritative monthly data-preparation boundary, after inspecting it. Do not edit or run the PowerShell rebuild without Anthony's explicit order.
- Validate required columns, row widths and types, period consistency, row counts, expected totals, JSON parseability, and a safe maximum payload size before publishing.
- Write a dated immutable data file into DATA. Preserve prior periods for history and rollback.

### 3. Build the isolated Cloudflare Worker project

- Create the Worker project in WEB with static assets and a same-origin request router. Bind a KV namespace for versioned report data and the current-version pointer. Add the selected strongly consistent Durable Object quota component.
- Implement `/r/<segment>/` routing for the shell, assets, `/api/health`, `/api/chat`, and the data endpoint. Unknown, malformed, and revoked segments return the same 404 response and reveal no route or data information.
- Resolve the segment to a non-personal cohort bucket using the external access map. Keep link values out of logs and responses; add `Referrer-Policy: no-referrer` and avoid third-party requests from the protected shell.
- Add bounded request bytes, message/history/context sizes, response bytes, upstream timeout, per-bucket message interval, and redirect rejection. Fail closed if quota or cohort validation storage is unavailable.
- Read the provider token only from the Worker secret binding. Pin model and provider endpoint server-side. Log only request metadata and outcome codes, never prompts, replies, tokens, or raw provider error bodies.
- Serve the current versioned report JSON only after access validation. Validate the pointer target and retain a known-good prior version for rollback.

### 4. Implement provider and quota behavior

- Match the current panel request contract where practical: bounded `message`, `history`, and aggregate `context`; do not accept a browser username as an authorization identity.
- Parse provider text and `usage` explicitly. Count prompt plus completion tokens from provider usage against the `gpr-web` app bucket and calendar month. Define behavior for absent or malformed usage as fail-closed.
- Warn in the panel at 80%; reject calls before they exceed the selected cap. Apply the per-bucket message interval.
- Return a consistent friendly user-facing state for provider 401/429 as required by the plan, while retaining safe operator diagnostics that distinguish quota exhaustion, invalid credentials, upstream rate limiting, and other failures.
- Ensure temporary cap overrides used for testing cannot be deployed as production configuration.

### 5. Add a hosted build while preserving the local build

- Add a build mode or hosted shell generator using the existing `build\build.mjs` sources. The local mode must continue embedding the data and setting `RELAY` to `http://127.0.0.1:8765`.
- The hosted shell must keep API calls inside the cohort prefix. Use a relative `RELAY = './api'` (or an equivalent explicit prefix) so a page at `/r/<segment>/` calls `/r/<segment>/api/...`; a root-absolute `/api` would lose the cohort segment. Load the authorized versioned data route. The page must not contain embedded purchase rows if those rows are served separately.
- Keep the dashboard's existing interface and aggregate-only assistant context. Preserve `textContent` rendering, in-memory chat history, and user-confirmed filter chips.
- Ensure all required local assets are served under the protected prefix and that shared/generated files do not contain the cohort map or Qwen token.

### 6. Publish data and deploy manually

- Validate the DATA artifact and record its period, schema version, row count, and reconciliation totals before upload.
- Upload a new immutable version first, confirm it can be read, then update the current-version pointer. Retain the prior pointer/version and document rollback.
- Deploy the WEB Worker separately from the monthly DATA update. Do not configure GitHub auto-deploy in this phase.
- Store `QWEN_TOKEN` and the hashed-segment `COHORT_MAP` with the Wrangler secret mechanism from the off-Desktop clone only. Never echo, inspect, or capture secret values in output.
- Before the first push or live deployment, recheck the selected GitHub account, repository owner, current diffs, secret destination, and cohort routing configuration.

### 7. Verification gates

All gates must pass before issuing links or calling the online version ready:

1. **Credential scan:** scan WEB, DATA, generated assets, deployment output, and logs for the provider token prefix and known secret patterns; zero hits.
2. **Authorized load and chat:** fresh headless Chromium opens a valid cohort link, loads report data, receives a real Qwen reply, and records provider usage in the quota store. Account for the provider-token cost before running this live check.
3. **Unknown path:** malformed and unknown cohort paths return 404 and cannot retrieve shell assets, report JSON, health, or chat.
4. **Revocation:** revoke one cohort and confirm its page, assets, data, health, and chat routes stop working while another cohort remains usable.
5. **Quota:** with an isolated test bucket and temporary low limit, calls warn at 80%, stop at the limit, and fail closed on storage errors. Dashboard data remains available while chat is quota-blocked. Include concurrent-call coverage for the chosen quota backend.
6. **Inert model output:** inject an `<img onerror>`-style response and verify it renders as text with no execution.
7. **Usage limits:** review request and storage usage against current Cloudflare plan limits after initial use; record a monthly review task.
8. **Local sibling unchanged:** rebuild or verify the existing `file://` artifact according to the project's established procedure and confirm it still works offline without the relay and still uses the shared `:8765` relay when available. Do not run build scripts until separately authorized.
9. **Data rollback:** publish a test version in a non-production namespace or equivalent isolated test, switch the pointer, and verify the prior version can be restored without serving a partial file.
10. **Mobile/Safari:** verify layout, data loading, and assistant states in a current Safari or mobile browser as required by the design.
